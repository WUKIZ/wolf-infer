# 设计说明

## 定位

在 **16 GB 显存的 DCU** 上跑 **14.3B MoE**。目标不是最快的推理引擎，是
「在给定的内存预算下，先把模型跑起来，再自动选最合适的档位」。

对比：vLLM 假设显存装得下权重；ktransformers 面向 x86 + Intel AMX。
本项目面向国产卡 + 小显存，这是两者的空白。

## 三种驻留模式

| 模式 | 专家在哪 | 适用 | 实测 |
|---|---|---|---|
| `resident` | 全在显存 | 显存放得下 | 10.83 tok/s（60 G 时期） |
| `pinned` | 全在主机内存（pinned） | 主机内存 ≥ 权重 × 3.4 | 6.32 tok/s 单流 |
| `stream` | 按需从磁盘换入 | 都放不下 | 1.16 tok/s |

`core/plan.py` 根据（总内存、显存、卡数、参数量）自动选模式，公式在文件顶部。
实测校准值：14B 模型预测 11.2 tok/s，实测 10.83，误差 3%。

## 为什么没有自定义 kernel

试过：按专家分组做 GEMM，B=32 用 PyTorch 是 15.6 tok/s，比逐专家循环的 60 还慢。
原因是 4320 次小算子（每层 60 专家 × 24 层 × 3 个矩阵乘）的启动开销吃掉了并行收益。

要拿到分组收益，必须写成**一个 fused kernel**。那是下一步，不是当前版本。
## 口径为什么这么定

所有吞吐数字都按 **「不同 prompt」** 测。

原因：MoE 的成本取决于 **专家并集大小**，不是批大小。
同一句 prompt 复制 N 份，并集退化成 4 个专家，吞吐会系统性高估 4–5 倍。
早期报告的 591.5 tok/s 就是这个错误，已作废。

判据也同样收紧：测试用例只看**第一条非空行**（模型选中的那个选项），
因为选项列表里本来就含正确答案，全文匹配会把答错算成答对。

## 批量 prefill

等长请求才能同批：不同长度的请求按 token 长度分桶，桶内一次前向。
64 条 20-token 请求：逐条 114.54 s → 批量 12.77 s（**9.0×**），末位 logits maxdiff 0.000000。

`last_only=True` 时只对末位算 LM head。收益与序列长度成正比：
256 token 时 3.6×，但 20 token 的短请求只有 1.08×——head 不是短请求的瓶颈。

## 已知缺陷

- KV cache 按 16 token 对齐分配，B=512 时浪费明显（2 的幂次对齐会直接 OOM）
- 无前缀缓存，多轮对话每次重算
- 无投机解码
- PP 只验证了管道（`core/pp.py` + `tests/pp_smoke.py`），未接进 `decode`
- EP 只买容量不买速度（B=32 时 26.24 vs 单卡 85）
