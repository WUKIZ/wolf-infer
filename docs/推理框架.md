# 规模无关推理框架 · 实测与边界（2026-10-28）

## 口径

- 硬件：单卡 DCU 64 G；容器 `memory.limit_in_bytes` **60.7 G**；盘 12 GB/s；PCIe 130 GB/s
- 模型：Qwen1.5-MoE-A2.7B —— 24 层 / d=2048 / 60 专家 top-4 / 共享专家 5632 / 总参 14.31 B / 激活 2.69 B / RoPE θ=1e6 / q,k,v **带 bias**
- 采样：greedy；对拍 max 48 token；性能与正确性**分开测**

|---|---|---|

## 正确性

- 5 条不同长度 prompt：`max abs diff 0.062–0.135`、`mean 0.001–0.019`、`top1 8/8`
- 短生成（≤16 token）逐字一致；48 token 长生成 5/8，首个分叉 @18 步，该步稠密 top1−top2 = **0.0000（完全并列）**
- 结论：分叉源于并列 token 在 bf16 累加下的取舍，非逻辑错误

## 瓶颈归因（关键）

单流每 token 需 96 个专家 × 3 张量 = **288 次独立读取**，共 1.66 GB；
实测 0.864 s/token → 有效带宽 **1.9 GB/s**（盘 12 GB/s 的 16%）。
⇒ **瓶颈是 safetensors mmap 逐页缺页的延迟，不是带宽，也不是注意力**。
批处理已把专家读共享（每层一次 `_moe`），仍无收益，进一步印证该归因。

## 单卡天花板

> 分页 MoE 的上限由**主机内存**决定：60.7 G 容器 1.16 tok/s；121 G 容器全量 pinned 6.32（单流）/ 28.81（B=8）。质变只有两条：双卡专家并行（每卡 12 G 常驻，目标 10 tok/s 级）或换大内存容器（全量 pinned）。

## 2026-10-29 内存定论（同一份代码，换容器即变）

| 配置 | tok/s | 条件 |
|---|---|---|
| 60.7 G 容器，无预热 | 1.16 | 每 token 288 次小读 |
| 121 G 容器，全量 pinned，单流 | **6.32** | `warm` 完成 1440 |

| 全驻留（历史） | 10.83 | 显存 26.7 G |

×25.6，全部来自内存档位，不是算法改动。

### 归因

- 无预热：每 token 288 次独立读取、1.66 GB，实测有效带宽 **1.9 GB/s**（盘 12 GB/s 的 16%）→ 缺页延迟主导
- 全量 pinned：B=8 时 attn 48% / moe 51% / other 1%；moe 侧 13 GB/步已贴 PCIe 带宽，**注意力侧是 Python 逐层循环**
- 之前 14 层被杀的原因**不是 memlock**：容器 `ulimit -l` 恒为 64 KB 且改不动，但 121 G 容器下全量 pinned 正常 → 真实原因是 cgroup 容量

### 坑（新增）

- **DCU 上 `F.scaled_dot_product_attention` 对 bool mask 走非原生回退，只发 warning、结果错误**（输出退化为重复 token）。已回滚为手动 `q@k.T → masked_fill → softmax → @v`
- safetensors 的 mmap 是逐页缺页，不是块读；这是无预热模式只有 1.9 GB/s 的原因
- `_pool` 原为 3 块共享缓冲，物理上无法跨请求去重；改为按层增长 + `(专家,张量)` 记忆后方可复用

### 未完成

1. ~~批量解码 bug~~ **误报**：`B=1` 输出 `\n`、`B=2` 输出 `..` 都是正确答案，只是打印的是末几个 token；带 memo 的半补丁版本才是真坏。现已回滚 memo，B=8 验证 8/8 一致
2. `core/plan.py` 接入 `KVEngine`，删除写死的 `pin_per_layer/resident` 默认值
3. 双卡 EP，目标 B=8 达 45–55 tok/s

### 硬/软二分

- 硬数据（不可调）：每参数 2 B、每 token 激活×2 B、VRAM/PCIe/盘带宽、容量
- 软数据（可调）：`pin_per_layer`、`resident`、batch、EP 度、实现达成率（现 5–26%）
- 由此：**容量 = (显存+内存+存储)/2B，速度 = 带宽/每token字节×达成率**；规模无上限，速度有下限

## 2026-10-29 CUDA Graph 负结果

DCU（ROCM/hipGraph，torch.cuda.CUDAGraph）捕获后与 eager 不等价：
- 同一状态（pos、tok、KV 全同）下 logits `maxdiff 5.94`，argmax 相同但数值已偏
- pinned 与 resident 两种权重来源数值完全一致 → 与 `_pool` 复用无关
- 同步拷贝 `non_blocking=False` 后数值不变 → 与异步丢序无关
- 图本身确定（同输入重放 diff 0.000000）且对输入敏感（换 token diff 16.75）
- 结论：捕获路径与 eager 存在语义差异，未定位到具体算子

收益虽大（277 ms/步 → 53 ms/步）但结果错误，**未采用**。文件归档在 `experiments/moe_graph.py`，换 DTK 版本或换卡时可直接复测。

## 2026-10-29 两条结构性优化（结果已验证）

| 版本 | tok/s | attn | moe | 说明 |
|---|---|---|---|---|
| pinned 基线 | 28.94 | 154.8 ms | 139.3 ms | 每步 277 ms |
| 专家 GEMM 合并 | 39.01 | 154.8 ms | 45.5 ms | `moe_block` 把命中的 K 个专家权重 `stack` 成 `(K,..)` 一次算 |
| + rope 查表 | **68.53** | **69.1 ms** | 43.0 ms | `_attn_b` 的 rope 从每请求 2 次调用改为整批查表 |

关键坑（两次都栽在同一处）：
1. `torch.stack([t[k] for k in keys])` 里 `t[k]` 返回的是**同一个共享缓冲**，列表里 K 个元素其实是同一对象 —— 必须 `.clone()`
2. `down_proj.weight` 是 `(d, inter)`，批量 `matmul` 要 `dw.transpose(1, 2)`

代价：每步 `pinned 288 个张量 ≈ 1.62 GB`，disk 0（全命中 pinned）。
